1 · System overview — boot → triggers → queue/direct → tables → consumers

Everything is started by index.ts at app.listen(). There is no external scheduler — each cron is a self-rescheduling setTimeout loop inside the Node process. Work reaches storage by one of three paths: price pollers (write quotes directly), producer crons (enqueue into the screener_jobs queue, drained by worker pools), or direct-compute crons (compute and write a table inline). API routes + client hooks read the resulting tables.

2 · Job-queue lifecycle — producer / worker / reaper

The async queue (screener_jobs) decouples rate-limited / intermittently-available upstreams (IB, Finnhub) from the crons that need them. Producers own retry policy & dedup; workers are pure executors. A producer runs two loops: a slow produce loop (enqueue deduplicated work) and a fast advance loop (drain finished rows, apply retry/finalize).

DRY / SOLID candidates spotted (for the planning dialogue)

  • Cron-scheduler boilerplate (DRY). ~20 crons hand-roll the same skeleton: FIRST_RUN_DELAY_MS + CADENCE_MS + a recursive setTimeout(loop, …).unref() + try/catch + notify. Candidate: one scheduleCron({ name, firstDelay, cadence, run }) helper.
  • Producer/queue pattern (DRY + SRP). The produce-loop (enqueue+dedup) / advance-loop (drainDone, drainFailed → markRetry/finalize) shape repeats across 4–5 producers. Candidate: a JobProducer base or factory carrying the retry policy.
  • Registry-by-side-effect (SOLID — DIP/explicitness). Handlers + gates register by mutating module-level maps at import time. Works, but import-for-side-effect is fragile and untestable in isolation. Candidate: explicit registration / a register() call wired in boot.
  • "Producer" naming overload (SRP/clarity). intradayRangeTraderProducer uses no queue (computes inline) while the others do. Same suffix, different contract.
  • Unused compute worker pool. Only noop is registered — dead capacity or a placeholder to retire/fill.
  • Shared-table writers (ISP/ownership). trait_scores has 3 writers, universe has many. Fan-in is fine, but worth a writer-ownership convention so columns aren't clobbered.
  • Client-side 6-table join in useVirtualList (already flagged in consumers.md Obs 1) — server-side endpoint candidate, but FE-side, out of the server Arch scope.

These are observations to discuss, not a committed plan. The full read/write matrix lives in spec/data/consumers.md.
